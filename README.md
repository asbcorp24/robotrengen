# ESP32-S3: мост STM32 UART ↔ телефон BLE

Первая реализация транспорта на установленном pioarduino / Arduino-ESP32 3.3.12.
BLE работает через встроенную библиотеку NimBLE. PlatformIO устанавливает ArduinoJson.
По UART передаётся CBOR, по BLE передаётся JSON в UTF-8. ESP32 преобразует
формат в обе стороны и сохраняет имена полей, тип сообщения и sequence.
Контроллер и приложение определяют смысл измерений, ошибок и команд.

## Прошивка плат

Откройте терминал PlatformIO в папке с `platformio.ini`. Для UART v3 прошейте
обе платы из одной версии проекта.

### ESP32-S3 через USB

Подключите ESP32-S3 кабелем USB с передачей данных. Если на плате два
USB-разъёма, используйте разъём UART. Команда `pio device list` покажет
COM-порт. В примере используется `COM14`.

```powershell
pio device list
pio run -e esp32-s3-devkitc1-n16r8 -t upload --upload-port COM14
```

Если загрузка остановилась на `Connecting...`, удерживайте BOOT, коротко
нажмите RESET/EN, отпустите BOOT и повторите команду. После `SUCCESS`
откройте монитор и нажмите RESET/EN. В логе появятся `BLE: Crawler-…`
и `UART protocol=3`.

```powershell
pio device monitor -p COM14 -b 115200
```

Закройте монитор через Ctrl+C перед повторной прошивкой.

### STM32 Blue Pill через ST-LINK

Подайте питание на Blue Pill и соедините программатор с платой.

| ST-LINK | Blue Pill |
|---|---|
| SWDIO | PA13 |
| SWCLK | PA14 |
| GND | GND |
| NRST, если есть | RST |

Подключите ST-LINK к компьютеру, закройте другие утилиты, которые используют
программатор, и выполните команду. COM-порт для ST-LINK не нужен.

```powershell
pio run -e bluepill_f103c8 -t upload
```

Если PowerShell не находит `pio`, добавьте PlatformIO в PATH на время
этого сеанса и повторите команду:

```powershell
$env:Path = "$env:USERPROFILE\.platformio\penv\Scripts;" + $env:Path
```

## Подключение плат и проверка

| ESP32-S3 UART1 | Blue Pill USART1 |
|---|---|
| GPIO17 (TX) | PA10 (RX) |
| GPIO18 (RX) | PA9 (TX) |
| GND | GND |

UART работает на **115200, 8N1** с логическими уровнями **3,3 В**.
В мониторе ESP32 счётчик `UART rx` растёт при приёме телеметрии от Blue Pill.

Устройство рекламируется как `Crawler-XXXXXX` (суффикс из заводского MAC).
Телефон: соединиться, завершить pairing/bonding, подписаться на TX notifications,
затем отправить Hello, SchemaRequest и SnapshotRequest. До шифрования и подписки
команды на STM32 не передаются. После переподключения эти запросы повторяются.

## BLE GATT

| Назначение | UUID | Свойства |
|---|---|---|
| Service | `82b10001-95c4-4f26-a9db-96ef80e73210` | — |
| RX, телефон → ESP32 | `82b10002-95c4-4f26-a9db-96ef80e73210` | Write with response, encrypted |
| TX, ESP32 → телефон | `82b10003-95c4-4f26-a9db-96ef80e73210` | Notify, только после шифрования |
| INFO | `82b10004-95c4-4f26-a9db-96ef80e73210` | Read, encrypted, JSON |

CCCD создаёт NimBLE автоматически. Запрашиваемый MTU — 247; поддерживается и
стандартный MTU 23. Каждая RX write / TX notification содержит **один фрагмент**:

| Смещение | Размер | Значение |
|---|---|---|
| 0 | 2 | message_id |
| 2 | 2 | полная длина raw packet |
| 4 | 2 | смещение данных в raw packet |
| 6 | до MTU − 9 | данные |

Все поля заголовка little-endian. `message_id` увеличивается для нового сообщения
и может переполняться. Фрагменты одного сообщения идут последовательно. Смещение
0 начинает новое сообщение и отменяет недособранное. Повторы ненулевого смещения,
пропуски, смена ID или длины сбрасывают сборку. Таймаут сборки — 1 секунда от первого
фрагмента. Телефон реализует такой же алгоритм сборки TX.

Не используйте GATT long/prepared writes: отправляйте отдельные write-with-response
размером не более согласованного MTU − 3, максимум 244 байта. Дождитесь завершения
предыдущей write. Подтверждение ATT означает получение фрагмента стеком, а не
постановку команды в очередь и не её выполнение.

## Пакеты BLE v2 и UART v3

| Смещение | Размер | Значение |
|---|---|---|
| 0 | 1 | версия, `2` по BLE, `3` по UART |
| 1 | 1 | тип сообщения |
| 2 | 2 | flags, зарезервировано, строго `0` |
| 4 | 2 | длина payload, 0…1024 |
| 6 | 4 | sequence |
| 10 | N | payload, объект JSON UTF-8 по BLE или карта CBOR по UART |
| 10 + N | 4 | CRC32 заголовка и payload |

Целые числа заголовка и CRC передаются little-endian. Длина payload измеряется
в байтах выбранного формата. Запрос без параметров содержит `{}` по BLE
или пустую карту CBOR `A0` по UART.
CRC-32/ISO-HDLC: reflected polynomial `0xEDB88320`,
init `0xFFFFFFFF`, xorout `0xFFFFFFFF`, refin/refout true.
Проверочный вектор ASCII `123456789` → `0xCBF43926`.

Raw packet имеет длину 14…1038 байт. По **UART** он передаётся как
`COBS(raw_packet) + 0x00`, максимум 1044 байта с разделителем.
По **BLE** фрагментируется именно raw packet, без COBS и без разделителя.
Пакеты с неверной версией, flags, длиной или CRC отбрасываются.
Обновите обе прошивки для UART v3. Формат BLE v2 и UUID характеристик сохраняются.
Версия BLE доступна в поле `protocol` характеристики INFO.

`sequence` — идентификатор сообщения источника. Мост сохраняет его и
пересчитывает длину и CRC после преобразования payload.
Проверка дублей команд, request_id, сессий, дедлайнов и повторная выдача результата
обязательны на STM32. Мост не выполняет команды и не формирует CommandResult.
Для управляющих действий нужен также монотонный номер намерения внутри сессии:
после Stop STM32 отклоняет более старые запросы запуска, даже если телефон повторил
их после остановки. Для ручного движения свежесть подтверждает короткоживущее
разрешение STM32; мост не создаёт и не продлевает такое разрешение.

## Типы сообщений

| Код | Имя | Направление через мост |
|---|---|---|
| `0x01` | Hello | оба направления |
| `0x02` | SchemaRequest | телефон → STM32 |
| `0x03` | Schema | STM32 → телефон |
| `0x04` | SnapshotRequest | телефон → STM32 |
| `0x10` | Telemetry | STM32 → телефон |
| `0x11` | ErrorsSnapshot | STM32 → телефон |
| `0x12` | ErrorEvent | STM32 → телефон |
| `0x20` | Command | телефон → STM32 |
| `0x21` | Stop | телефон → STM32, приоритетная очередь |
| `0x22` | CommandResult | STM32 → телефон |
| `0x23` | EventAck | телефон → STM32 |
| `0x40` | LinkState | только ESP32 → STM32 |

Неизвестные типы транспортных сообщений и запрещённые направления отбрасываются.
При добавлении ключей телеметрии/ошибок новые типы сообщений не требуются.
ESP32 принимает карты CBOR со строковыми ключами и определённой длиной.
Поддерживаются числа, строки UTF-8, логические значения, null, массивы и вложенные карты.
Лимит payload в 1024 байта действует для каждого формата отдельно. Большие
реестры делите на части, чтобы каждый пакет помещался и в CBOR, и в JSON.

Телефон собирает BLE-фрагменты, проверяет длину и CRC, декодирует payload
как UTF-8 и разбирает JSON. Для команды телефон формирует пакет из JSON,
номера последовательности и типа запроса.

Blue Pill и Python-симулятор используют следующие ключи в CBOR.
ESP32 передаёт эти же ключи телефону в JSON:

```text
Hello (ответ):   device_id, boot_id, schema_revision
SchemaRequest:   {}
Schema:          revision, part_index, parts_total, fields (массив)
SnapshotRequest: {}
Telemetry:       boot_id, sample_ms, values (объект)
ErrorsSnapshot:  boot_id, revision, active (массив)
```

Пример Telemetry:

```json
{
  "boot_id": 1,
  "sample_ms": 1200,
  "values": {
    "drive_battery_voltage": 24700,
    "drive_battery_temperature": 35,
    "distance": 500,
    "moving": true
  }
}
```

Элемент массива `fields` содержит `id`, `key`, `name`, `type`, `unit`, `access`
и `period_ms`. Каждый ключ в `values` соответствует `key` из реестра.
Новые измерения добавляются на STM32 в реестр и в объект `values`.
Приложение может отобразить новые поля по реестру.

`LinkState` по UART содержит CBOR с полями `boot_id`, `generation` и `ready`.
Он отправляется при загрузке ESP32 и изменении соединения/готовности.
`ready` означает соединение + шифрование + подписку TX. Это информационное сообщение,
оно **не продлевает разрешение ручного движения**. Generation — локальное поколение
транспорта ESP32: меняется при соединении, отключении, смене шифрования или подписки.
Это не замена сессии управления STM32.

## Очереди и восстановление

- BLE callback только копирует фрагмент в ограниченную очередь из 16 элементов.
- Полные пакеты обрабатываются в `loop()`, память протокола ограничена статически.
- Телефон → STM32: Stop (1 пакет), затем LinkState, затем обычные запросы (8 пакетов).
- Stop удаляет ранее ожидающие запросы; уже передаваемый UART-кадр завершается.
- Команды Command/Stop старше 250 мс от приёма первого фрагмента до начала UART TX
  отбрасываются. На передачу уже начатого UART-кадра нужно дополнительное время.
- STM32 → телефон: ответы/ошибки/реестр (8 пакетов) приоритетнее телеметрии (4 пакета).
- При переполнении телеметрии удаляется самый старый пакет. Мост не объединяет
  поля: STM32 должна периодически передавать полные снимки небольших групп.
- Приоритетный ответ может прервать фрагментацию телеметрии: его offset=0 начинает
  новое сообщение. Прерванный снимок восстанавливается следующим обновлением.
- При переполнении остальных очередей новый пакет отбрасывается; растёт счётчик.
  Телефон повторяет запрос с тем же request_id; STM32 должна устранять дубли.
- Неуспешная отправка BLE-фрагмента отменяет сообщение. Мост не повторяет его
  вслепую. Для ошибок/результатов нужны подтверждения и повторы конечных устройств.
- На смене соединения или готовности очищаются очереди и недособранные BLE-пакеты.
  Данные со старым generation не принимаются. Старые команды не воспроизводятся.
- Пока телефона нет, поступающая телеметрия не сохраняется. После подключения
  телефон явно запрашивает новый реестр/снимок/список ошибок.
- Неполный UART-кадр после паузы 250 мс отбрасывается до следующего разделителя.

Раз в 5 секунд Serial выводит счётчики приёма, CRC/форматных ошибок, потерь очереди,
просроченных сообщений, ошибок уведомлений и свободную heap.

## Проверка без STM32

```powershell
# Нативные тесты настоящего C++ модуля протокола; нужен g++ либо clang++.
python tools/test_protocol.py
# После сборки Blue Pill можно также проверить преобразование форматов.
python tools/test_protocol.py --payload

# Примеры пакетов и BLE-фрагментов в hex без внешних зависимостей.
python tools/stm32_simulator.py --example

# Подключить отдельный USB-UART вместо STM32: TX адаптера → GPIO18,
# RX адаптера ← GPIO17, общий GND, 3,3 В. COM7 — пример.
python -m pip install pyserial cbor2
python tools/stm32_simulator.py --port COM7
```

Симулятор отправляет телеметрию и пустой список ошибок раз в секунду, отвечает на
Hello/SchemaRequest/SnapshotRequest. Любую Command/Stop отклоняет с причиной
`simulator_no_actuators`. В этом ответе для стенда sequence равен sequence запроса;
это не окончательная спецификация request_id управляющих команд.

Проверка с телефоном: pairing → подписка TX → передача hex фрагментов из `--example`
для SnapshotRequest → сборка ответных уведомлений → проверка CRC и разбор JSON.
BLE-терминал должен писать **байты hex**, а не строку с шестнадцатеричными символами.

## Проверка на STM32 Blue Pill

Прошивка `src/bluepill/main.cpp` имитирует контроллер на STM32F103C8T6.
Blue Pill передаёт телеметрию каждые 200 мс и снимок
активных ошибок раз в секунду. `Hello`, `SchemaRequest` и `SnapshotRequest`
возвращают идентификатор стенда, реестр полей и текущие значения соответственно.
Идентификатор загрузки в стендовой модели фиксирован. Состояние модели
хранится в RAM и сбрасывается при перезагрузке.

После сопряжения и подписки на TX можно проверить ответы на команды:

| Тип пакета | JSON payload | Что происходит |
|---|---|---|
| Command `0x20` | `{"op":"start"}` | Счётчик расстояния растёт, пока модель движется |
| Stop `0x21` | `{}` | Счётчик останавливается |
| Command `0x20` | `{"op":"raise_fault"}` | Появляется ошибка 1, движение модели прекращается |
| Command `0x20` | `{"op":"clear_fault"}` | Ошибка 1 снимается |

Пока ошибка активна, запуск возвращает `rejected` с причиной
`simulated_fault_active`. При успешной команде приходит `completed`.
`CommandResult` повторяет sequence запроса. Команды меняют только модель в RAM.

Получить примеры готовых BLE-фрагментов:

```powershell
python tools/stm32_simulator.py --example
```

Выберите `phone_simulated_start`, `phone_simulated_stop` или `phone_snapshot_request`.
По очереди запишите строки из `ble_mtu23_hex` как hex-байты в RX с подтверждением записи.
При работе через своё приложение сериализуйте JSON в UTF-8 и сформируйте пакет
v2 с новым sequence.

## BLE-тестер для компьютера на Python

На Windows запустите `start_ble_tester.bat` из корня проекта. При первом
запуске он создаст окружение Python и установит Bleak. Для запуска вручную
выполните в PowerShell:

```powershell
python -m venv .venv-ble
.\.venv-ble\Scripts\python.exe -m pip install "bleak>=1.1,<4"
```

Запускайте тестер так:

```powershell
.\.venv-ble\Scripts\python.exe -m tools.ble_tester
```

Отключите телефон от ESP32, поскольку прошивка принимает одно BLE-соединение.
В тестере нажмите «Поиск», выберите `Crawler-…` и нажмите «Подключить».
Подтвердите сопряжение, если Windows его запросит. Тестер сам читает версию
протокола, подписывается на TX и запрашивает реестр и снимок.

Таблица показывает значения, единицы и время последней телеметрии. Кнопки
«Старт», «Стоп», «Вызвать ошибку» и «Снять ошибку» отправляют команды модели
Blue Pill. Запись «Отправлено» означает успешную запись в BLE RX. Результат
STM32 появляется отдельной строкой «Ответ» с тем же `seq`.
Для тестера нужен BLE-протокол v2 с JSON.

## Границы первой реализации

Реализован транспорт, а не полный контроллер безопасности из ТЗ.
Pairing запрашивает LE Secure Connections + bonding, без ввода кода (Just Works).
Требуются шифрование и 128-битный ключ. **Привязка к единственному владельцу,
защита MITM и окно сопряжения по физической кнопке ещё не реализованы.** Одно
активное соединение не запрещает другому телефону подключиться после отключения.
Локальный PIN приложения не заменяет аутентификацию устройства.

После шифрования соединения ESP32 запрашивает LE Coded PHY в обоих
направлениях. S=8 задаётся как предпочтение для передачи ESP32. Режим
зависит от возможностей второй стороны. Поиск устройства использует
обычную рекламу LE 1M.

В Serial Monitor строка `BLE PHY request=Coded S=8 status=0` означает,
что стек принял запрос. Строка `BLE PHY update … status=0 TX=Coded RX=Coded`
подтверждает переход обоих направлений на Coded PHY. Событие сообщает тип PHY
без указания S=2 или S=8. Если переключение не согласовано, соединение может
продолжать работать на исходном PHY. Параметр `kPreferCodedPhyS8` находится
в `include/Config.h`. Дальность 3 км и частоты обмена требуют измерений
с конкретным телефоном или адаптером.

До управления реальным кроулером STM32 должна реализовать состояния, аппаратные
и программные блокировки, дедупликацию, проверку свежести/сессии команд, собственный
таймаут ручного движения и двухэтапный запуск экспозиции. Счётчик sequence и
таймаут очереди ESP32 сами по себе этого не обеспечивают.
В этом изменении выполнены сборка и нативные тесты; связь на физическом оборудовании
пока не проверялась.
